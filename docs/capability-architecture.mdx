# Capability Architecture

The single rule that prevents every confusion below:

> **Execution site is dictated by the *invocation mechanism*, not by which folder a file sits in.**

The `sandbox/` folder is *conventional staging* for files the agent uses inside
the workspace. It does **not** mean "anything filed here runs in the sandbox." An MCP server
whose source lives under `sandbox/` still runs **host-side** (stdio) or **externally**
(sse/http).

---

## 1. The execution sites

Code executes at one of two *live* sites: the **host process**, or an **external daemon**.
The table below enumerates the *invocation mechanisms* and the site each one lands at.
Memorize it. (A third site — a Docker sandbox container — existed pre-fold and is retired;
see the historical note below.)

| Code lives at (file) | Invoked by | Actually executes at | What it sees |
| --- | --- | --- | --- |
| `src/tools/registry.py` (**REGISTRY**) | LLM tool call → in-process factory | **host process (dcode)** | runs against the workspace through the sandbox backend — deepagents `LocalShellBackend` (`src/sandbox/local.py`), host fs, **no container** |
| `profiles/<org>/sandbox/*.py` (a script) | the agent's `execute`/bash tool | **the workspace (host fs)** | same host fs as the repo; paths under the project root |
| **stdio MCP server** (source anywhere) | declared `capabilities:` / `tool_servers` `transport: stdio` | **host-side** (dcode forks it) | full host env (`os.environ`), host fs, host cwd |
| **sse/http MCP server** (external daemon) | declared `capabilities:` / `tool_servers` `transport: sse\|http` | **wherever the operator runs the daemon** | that daemon's environment |

Source references:
- REGISTRY in-process factories: `src/tools/registry.py`
- workspace scripts run under the local backend: `src/sandbox/local.py` (`local_backend`), selected in `src/sandbox/exec.py` (`PUX_SANDBOX=local` default; `openshell` optional)
- stdio children forked host-side by dcode's own loader: `src/run.py` (`_load_mcp` → deepagents `resolve_and_load_mcp_tools`)

**Historical (pre-fold harness, retired 2026-08).** Execution used to happen at three
sites: harness process, a **Docker sandbox container** (`docker exec`, container fs at
`/sandbox/workspace`), and external daemons. The container site is gone: the sandbox is now
deepagents' `LocalShellBackend` on the host filesystem. **Declared sandbox tools**
(`sandbox/tools/tools.yaml` → synthesized `pux_sandbox_<name>` `StructuredTool`s whose `func`
`docker exec`'d a script in-container) are retired with it — any `tools.yaml` files still
lying under `profiles/**/sandbox/` are dormant data no code reads. The typed, by-name,
auto-documented channel for a weak model is now MCP (stdio host-side, or external
sse/http) plus the REGISTRY specialists.

## 2. How capability is added

| You want to add… | Path | Project-portable? | Notes |
| --- | --- | --- | --- |
| **Custom agents** | org-local `agents/*.md`, `extends:` a base, `org.yaml` roster | ✅ | full override/inheritance grammar (`tools_add`/`tools_remove`/`model`/`prompt_append`/`skills_add`/`tool_description_overrides`) |
| **Custom skills** | `profiles/<org>/skills/*/SKILL.md` | ✅ | surfaced to the model via the `list_skills` specialist tool + deepagents `SkillsMiddleware` → `read_file` |
| **Custom tools (structured/foreign)** | MCP `tool_servers` — inline in `policy.yaml` or the catalog | ✅ | typed, model-callable; the godot-mcp path |
| **Custom tools (unstructured scripts)** | `profiles/<org>/sandbox/*.py` via the agent's `execute` | ✅ | the invest / cpp_globber path |
| **Custom tools (harness-native `ToolSpec`)** | edit `REGISTRY` in the library (`src/tools/registry.py`) | ❌ | rare; only for tools that bind the sandbox backend / `vision_model` / org |

**Override axes for tools are already unified with agents** under the same frontmatter-delta
grammar: `tools:` allowlist (selection), `tool_description_overrides` (per-key description
rewrite), `excluded_tools` (profile pruning). You do not need a separate "tool override"
system — it is the same `extends:` vocabulary.

## 3. Tool taxonomy in detail

### 3a. Harness-native tools — `REGISTRY`

The single global source of truth for tool *implementations*:
`src/tools/registry.py`.

- One `ToolSpec = {slug, category, requirements, factory, …}` per tool, declared **once**.
- Everything else (the `SPECIALISTS` / `NATIVE_FS_TOOLS` / `GRADERS` name sets, the prefix
  helpers, `make_specialist_tools`, `classify_slug`, `resolve_tool_allowlist`) **derives**
  from that list. No second copy.
- Categories:
  - `NATIVE` — `ls`, `read_file`, `write_file`, `edit_file`, `glob`, `grep`, `execute`.
    `factory=None`; injected by deepagents `FilesystemMiddleware`.
  - `SPECIALIST` — `python`, `list_skills`, `describe_image`, `multimodal`,
    `multimodal_mega`, `desktop_*`. Factories bind
    `sandbox`/`vision_model`/`org` as declared in `Requirements`.
  - `GRADER` — `pux_grader_*` evidence tools for `RubricMiddleware`.
- An agent's frontmatter `tools:` is an **allowlist** (selection from this set), resolved by
  `resolve_tool_allowlist` (`src/tools/registry.py:159`). It is **not** a definition.
- Adding one = add one `ToolSpec` line; every name set + resolver + builder updates
  automatically. This is intentionally a **library edit** (these tools bind harness
  internals; org dirs are declarative *data*, forbidden from importing internals by the
  compile-time surface).

### 3b. MCP tool servers — foreign, typed tools

Declared per-org, resolved to `ToolServerSpec`s, bridged to namespaced `BaseTool`s
(`mcp__<server>__<tool>`). Two declaration styles:

- **Catalog ref** — `tool_servers: [web_research]` → `profiles/_shared/tool_servers.yaml`.
  The catalog is **per-project** (resolved via `src/profiles/_paths.py`:
  `project_root()/"profiles"`, which respects `PUX_PROJECT_ROOT`).
- **Inline** — `tool_servers: [{name: …, kind: mcp, transport: …, …}]` directly in
  `policy.yaml`. No catalog needed; fully self-contained and export-portable.

Resolver: `src/protocol/mcp.py` (`_org_mcp_servers`).
Load bridge: `src/run.py` (`_load_mcp` — the org's refs are projected onto a temp
`.mcp.json` and loaded through dcode's own `resolve_and_load_mcp_tools`, fail-loud per
server).

**Transport semantics** (see §4 for the resolved stack):

| transport | requires | runs at | dcode spawns it? |
| --- | --- | --- | --- |
| `stdio` | `command` (+`args`,`env`) | **host-side** | yes — `resolve_and_load_mcp_tools` forks it from the host process |
| `sse` | `url` | external daemon | no — dcode dials the URL |
| `http` (Streamable HTTP) | `url` | external daemon | no — dcode dials the URL |

Per-server isolation: a server that is unreachable or fails `tools/list` contributes **zero**
tools + a loud `ERROR` log; it does not crash the org.

**Historical.** The pre-fold harness's MCP client (`McpSessionManager`) additionally shipped
a `github:` release-bootstrap block on stdio catalog entries (on-demand binary download
keyed by `{os}`/`{arch}` tokens, cached under `.pux/mcp-servers/`). Retired with that client
at the 2026-08 fold — stdio servers are now forked by dcode's own loader, which has its own
discovery story. The `env`-substitution semantics and per-server isolation survive
unchanged in `_load_mcp`.

### 3c. Sandbox scripts — in-workspace, unstructured

Plain Python (or any) programs in `profiles/<org>/sandbox/`, invoked by the agent through its
`execute`/bash tool. They run in the **workspace** (host fs via `LocalShellBackend`) and see
the project filesystem — the same fs the repo lives on.

- The canonical heavy example: `profiles/specialists/invest/sandbox/` — a 17-module quant
  pipeline (`fetch_data`, `signals`, `regime`, `walkforward`, `risk`, `trade`, `journal`, …)
  + `run_scan.sh`, all driven via `python3 sandbox/<m>.py <subcommand>`.
- The model does **not** see these as tools. It must know the CLI (documented in `AGENTS.md`
  / agent frontmatter / skills) and emit shell. Args are untyped strings.
- This is the right choice for utilities and domain programs. It is the *wrong* choice if you
  need structured, typed, by-name tool calls — use MCP for that.

**From the agent's perspective**, a sandbox script is *not* a tool — it is just another
thing to `execute`. REGISTRY and MCP tools are **auto-documented**: the host injects each
tool's description + JSON-schema into the model's tool list automatically (from the `factory`
for REGISTRY, from `tools/list` for MCP). A sandbox script enters the model's context **only
through prose** (AGENTS.md, agent frontmatter, a skill) — there is no schema, no arg
validation, no automatic discovery. This is the deliberate tradeoff of the "just exec"
channel: maximum simplicity, zero protocol overhead — at the cost of typed discovery. The
real risk is **prose/script drift** (the doc says `--rank` but the script now expects
`rank`); mitigate with **self-describing CLIs** (`argparse --help`, a `list` subcommand) the
agent can call so the script documents itself at runtime, from its own truth. If you need
auto-documented, schema-validated discovery, use MCP (or add a REGISTRY spec) — the typed
channels; choosing raw bash is choosing *deliberately not* to get typing.

### 3d. Skills — declarative procedures, not callable tools

`profiles/<org>/skills/*/SKILL.md` (+ optional `scripts/`, `references/`). Surfaced to the
model as metadata via the `list_skills` specialist tool + deepagents `SkillsMiddleware`;
bodies are peeked through the native `read_file`. Skills are **documents**, not
function-call tools.

### 3e. Declared sandbox tools — RETIRED

**Historical (pre-fold harness).** A fourth channel once existed: a per-org
`sandbox/tools/tools.yaml` **declared** tools (name + description + script + typed args);
the harness synthesized a langchain `StructuredTool` per entry whose `func` `docker exec`'d
the script **in-container**, and the model called `pux_sandbox_<name>(typed, args)` directly.
It existed for the case that needed *both* typing *and* in-container execution (REGISTRY was
typed but host-side; sandbox scripts were in-container but unstructured). It came with an
exec-guard (`RoutingMiddleware` redirecting raw `execute` of declared scripts), a
`returns: json` lesson (typed stdout parsing), and a `validate_declared_tools` offline
contract. **All retired with the container sandbox at the 2026-08 fold.** The weak-model
rationale survives as guidance: for a weak model, prefer typed, by-name, auto-documented
channels (MCP / REGISTRY specialists) over raw `execute` with hand-quoted args.

## 4. The MCP resolved stack (stdio is fully wired)

The whole chain from declaration to subprocess spawn:

```
resolver  src/protocol/mcp.py (_org_mcp_servers)   org capabilities: mcp refs → .mcp.json entries
   ↓
projection  temp .mcp.json written at launch        (src/run.py; kept for the process lifetime)
   ↓
loader    deepagents resolve_and_load_mcp_tools(explicit_config_path=…)
          dcode's OWN loader — full trust, no project-discovery, no approval prompts
   ↓
mcp SDK   StdioServerParameters(command, args, env, cwd) / sse / http sessions
```

`_load_mcp` (src/run.py) is **fail-loud per server**: every declared server must come back
with status `ok`; a skipped server raises with the reason named — an org's declared MCP
surface can never silently shrink.

### The host-side finding (important)

Because stdio sessions are forked from the host process, the stdio child inherits the
**host environment** and runs **host-side**. Consequences:

- For **godot-mcp** this is *favorable*: it needs `ws://localhost:6505` to reach the Godot
  editor, and the npx child's `localhost` = the host loopback = where the editor runs. The
  "local only" constraint is satisfied automatically. No bridging.
- For **project-local stdio MCP servers**: they see **host** fs/env, **not** a sandbox.
  A stdio "deploy" tool operates on host files; a tool that must edit the workspace should
  instead be a native fs tool (`read_file`/`edit_file`).

> **Post-fold note.** Pre-fold, this chain was the harness's own resolver + hand-rolled
> `McpSessionManager` bridge; the 2026-08 fold replaced both with dcode's
> `resolve_and_load_mcp_tools`. The transport semantics and the host-side finding above are
> unchanged.

## 5. Extending an org per-project (portability)

**You do not need to edit the global library to specialize an org.** Agents, skills, MCP
tools, and sandbox scripts are all project-portable.

### What the marketplace plugin bundles per org

`src/plugins/marketplace.py` (`emit_plugin` / `emit_marketplace`, the `pux compile
--marketplace` lane) carries, per org: `AGENTS.md`, `org.yaml`, `profile.yaml`,
`policy.yaml`, `agents/*.md`, `skills/*/SKILL.md`, `sandbox/*.py`, `config/` — **plus**
resolved shared dependencies (`profiles/_shared/agents/*.md`, `profiles/_shared/skills/`,
`profiles/_shared/sandbox/`) **and** `tool_servers.yaml` when the policy declares
`tool_servers`.

So an exported org is self-contained: its agents, skills, scripts, and MCP
catalog/declarations all travel.

### The co-pilot engine pattern

1. Ship the engine as a base org, emitted as an installable marketplace plugin
   (`pux compile --marketplace`; `src/plugins/marketplace.py`) with a minimal CTO +
   extends-friendly roster + default profile.
2. A consuming project installs the plugin and/or sets `$PUX_ORG_PATHS` (or uses local
   `profiles/`) and declares a thin local org: `extends: <base>`.
3. The project specializes **without touching the library**:
   - custom agents → local `agents/*.md` extending base roles
   - custom skills → local `skills/`
   - custom tools → **inline** MCP `tool_servers` in `policy.yaml`
4. The `pux:` namespace resolves against shipped library bases **or** `$PUX_ORG_PATHS` roots
   (`src/profiles/_paths.py`).

### Inline tool server (the portable structured-tool pattern)

```yaml
# profiles/specialists/<my-org>/policy.yaml — inline, export-portable, no library edit
tool_servers:
  - name: proj_tools
    kind: mcp
    transport: stdio
    command: python3
    args: [sandbox/proj_tools.py]   # a small FastMCP server with typed tools
```

This is the godot-mcp pattern generalized. The source file's location under `sandbox/` is
just where the bytes live in the repo — the server still runs **host-side** (stdio).

## 6. Decision rules — when to use what

Use this spectrum. Do not reach for MCP for simple utilities; do not use bash for complex
stateful systems.

| Need | Use | Example |
| --- | --- | --- |
| A quick local helper (one function, low risk, rarely called) | **sandbox script** via `execute` | `cpp_globber.py`, `clean_build.py` |
| A typed, model-callable tool for a foreign/stateful/complex system | **MCP** (`stdio` host-side or `sse`/`http` external) | godot-mcp (42 tools over websocket) |
| A typed in-workspace primitive for a weak model | **REGISTRY specialist** (library edit) or an MCP server | `python`, `multimodal` |
| A universal primitive every org needs, binding harness internals | **REGISTRY** `ToolSpec` (library edit, rare) | a new native fs/shell op |
| Config files, mock data, templates, local binaries staged in the workspace | **sandbox/** folder (non-script payload) | `.eslintrc`, seed DB, fixtures |
| A reusable procedure / playbook the model reads on demand | **skill** (`SKILL.md`) | "how to deploy this service" |
| A specialized agent role | **agent** (`agents/*.md`, `extends:` a base) | "cpp-developer", "playtester" |

**The cpp_globber test:** if the capability is a simple function, write a `sandbox/*.py`
script and let the agent run it through `execute`. Wrapping it in an MCP server is
over-engineering.

**The weak-model test:** if the model is weak (mimo-v2.5-class) and the script has
typed args it must recall and quote correctly, put it behind a typed channel (a REGISTRY
specialist or an MCP server) so the model calls it by name. Keep `execute` for genuinely
ad-hoc one-offs where a typed declaration isn't worth it.

**The godot test:** if the capability requires a persistent connection to a live external
system and exposes many operations, MCP is *less* complex than building a giant CLI parser.

## 7. Pitfalls & common confusions

1. **"Tools are defined once globally, so I must edit the library to add a tool."**
   True only for harness-native `ToolSpec` implementations. For project-specific tools, MCP
   (typed) or sandbox scripts (unstructured) are both project-portable and need no library
   edit.

2. **"The `sandbox/` folder means the code runs in a sandbox."**
   Only for scripts the *agent* invokes via `execute`. An MCP server filed under `sandbox/`
   runs host-side (stdio) or externally (sse/http). **The folder is staging; the mechanism
   decides where it runs.**

3. **"Put the FastAPI MCP server in `sandbox/` and start it via `host_setup`."**
   Pre-fold, `host_setup` ran host-side and produced *env vars* for the Docker container;
   it is retired with the container. sse/http servers are external daemons dialed by URL;
   stdio servers are host-side forks. **No mechanism starts an MCP daemon in a sandbox.**

4. **"Agents are composable but tools are monolithic."**
   The override-worthy parts of tools (description, selection, availability) are already
   unified under the same `extends:`/profile delta grammar as agents. Only tool
   *implementations* are global — and that is load-bearing (they bind harness internals;
   their name is a contract; one registry is what killed tool-name drift).

5. **"MCP = a big external server."**
   stdio MCP scales down to `python3 sandbox/my_tools.py` — a tiny local script with typed
   tools. "MCP" names the protocol/transport, not a deployment size.
